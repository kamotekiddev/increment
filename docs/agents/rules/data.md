# Data and correctness rules

1. **Save a set exactly as typed.** Each set stores the typed number (`weight`) and its unit (`weight_unit`); nothing is converted or rounded on save (ADR 0003). Targets are kg. A routine exercise's Jump is saved per unit in that unit (`step_kg`, `step_lb`). The unit preference is display only: switching it never writes a set. All kg/lb math lives in `src/units`, converts in memory only (records, volume, the engine work in kg), and a converted value is never written back. Round only weights about to be lifted (pre-fills, the Last column, Targets) down to the Jump, and only when they came from the other unit; history shows a set in the other unit as "≈" and one decimal, never a plate weight.
2. **Derive records, never store them.** Heaviest set, estimated 1RM and most volume are queried from `sets`. The Target shown at the start of a workout and whether the lifter accepted a step are not records: they are stored on `workout_exercises`.
3. **Keep the overload engine and unit conversion pure.** They take plain inputs and do no I/O. They don't touch React or the database. Every rule change comes with a unit test.
4. **Round targets to a multiple of the Jump.** The Jump is the routine exercise's one for the lifter's current unit (`step_kg` or `step_lb`, 2.5 kg / 5 lb while null; `jumpKgFor` in `src/units`), and a workout whose routine exercise was deleted uses that default. Switching unit never writes a Jump. The engine knows only the Jump, as kg, not plates or bar weight. A step up goes to the next multiple strictly above the current weight; a drop or deload rounds down. A Target set in another unit than the lifter's current one (Hold, Stay, on track, a baseline, an accepted stored Target alike) first rounds down to the largest multiple of the current unit's Jump at or below it, so it stays loadable: 62.5 kg with a 5 lb Jump is 135 lb, not 137.79 lb or 140 lb. A Target set in the current unit never snaps, even after its Jump changed. A small tolerance leaves a Target already on the grid untouched (so a float a hair below a multiple never drops a whole step), and bodyweight Targets (0) never change. A step up from a snapped Target goes one Jump above it (Stay 135 lb, Go up 140 lb). Each Target records the unit it was set in (`workout_exercises.target_unit`, and `accepted_target_unit` for an accepted Target, the unit at Go up; older rows fall back to their sets' `weight_unit`, then kg; a baseline uses its sets' unit), and the engine takes those units as plain inputs. The snap lives in the engine, so Start, the Today preview, the Offer and the summary agree; a snapped Target is a changed Target and restarts the Streak. Stored sets never change. A set logged in another unit than its Target (after a Settings change mid-workout) is judged against the Target as shown in the current unit, rounded down to the Jump the same way: a 62.5 kg Target lifted as the 135 lb shown (61.23 kg) is clean, 130 lb is a Hold. A set in the Target's own unit is judged against the stored Target.
5. **Every schema change is a Drizzle migration.** Never edit the database by hand or change a shipped migration. The backup file carries a format version. A version bump needs a matching import path for older files.

See `docs/architecture.md` for the data model, units and backup format.
